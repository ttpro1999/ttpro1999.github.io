Doubly Linked List Phase 1 – Khi kernel cần xóa task ngay lập tức

📅 Published: January 8, 2026
RTOS Data Structure Kernel Intrusive Pointer Arithmetic

(1) Bối cảnh thực tế – Vấn đề mới nảy sinh

Sau khi triển khai SLL, kernel chạy ổn định. Nhưng sau vài tháng, một yêu cầu mới xuất hiện: Priority Scheduling.

Các task giờ không còn chạy theo thứ tự FIFO. Thay vào đó, kernel cần sắp xếp task theo ưu tiên. Khi ISR hoàn thành một task, nó phải xóa task đó khỏi queue chính xác – không phải xóa “task có key = x”, mà xóa task cụ thể này mà ISR đang cầm con trỏ.

Scenario cụ thể: Tác vụ A đang chạy. ISR I/O hoàn thành cho task B (ưu tiên cao hơn A). ISR cần:

  1. Lấy task B khỏi I/O wait queue
  2. Xóa task A khỏi running queue (để task B chạy)
  3. Tất cả phải xong trong < 100ns (ISR latency budget)

Với SLL, xóa task A từ running queue cần:

// O(n) search + unlink
sll_remove(&running_queue, task_A);

Nếu running queue có 50 tasks, đó là 50 iterations trong ISR. Không chấp nhận được.

Điểm yếu của SLL khi ISR xóa task:

  • ISR có task pointer, nhưng SLL không thể dùng nó
  • Buộc phải search từ đầu → O(n)
  • Interrupt latency tăng vượt budget

“Kernel engineer không thể để ISR dependency vào danh sách dài.”

(2) Giải pháp ngây thơ – Thêm back pointer vào SLL

Ý tưởng đầu tiên: Thêm prev pointer vào SLL để có cả hai chiều.

SLL với back pointer:
task0 <-> task1 <-> task2

Xóa task1:
task0->next = task2
task2->prev = task0

Cấu trúc:

typedef struct task {
    struct task* prev;
    struct task* next;
    int priority;
    void (*entry)(void*);
} task_t;

Nghe ra O(1) rồi? Nhưng có một vấn đề căn bản: Dấu hiệu của design yếu đang nằm ẩn trong cách chúng ta tổ chức dữ liệu.

Với cách này, task_t phải “biết” nó đang nằm trong queue. Nhưng trong kernel thực tế, một task có thể nằm trong:

  • Ready queue (task sẵn sàng chạy)
  • Sleep queue (task đang sleep)
  • I/O wait queue (task đang chờ I/O)
  • …cùng lúc?

Không được – một task chỉ ở một trạng thái một lúc. Nhưng cấu trúc task_t có prev/next là hộp đen – code bên ngoài không biết nó đang được dùng ở queue nào.

“Khi dữ liệu phải biết quá nhiều về hạ tầng, kiến trúc đã bắt đầu rạn nứt.”

“Kernel engineer bắt đầu nhận ra: cấu trúc dữ liệu không phải chỉ về con trỏ, mà về tách biệt dữ liệu user từ cấu trúc queue.”

(3) Ý tưởng cốt lõi – Intrusive pattern sinh ra

Thay vì nhét prev/next vào task_t, tôi tách biệt chúng ra:

SLL (non-intrusive):
Kernel quản lý:  [node]---[node]---[node]
                  |        |        |
                  v        v        v
Dữ liệu user:  [task A] [task B] [task C]

DLL Intrusive:
Dữ liệu user:   [task A]      [task B]      [task C]
                | node |      | node |      | node |
                |{p,n} |<---->{p,n}  |<----->{p,n} |
                ^                                ^
                └──────── circular ──────────────┘

Chủ chốt: Node được nhúng sâu vào task_t nhưng về mặt logical tách rời – là một “passkey” để task có thể nằm trong queue mà không phải “biết” queue là gì.

Một task có thể có nhiều node trong cấu trúc:

typedef struct task {
    int priority;
    void (*entry)(void*);
    
    dll_node_t ready_node;    // khi sẵn sàng chạy
    dll_node_t sleep_node;    // khi đang sleep
    dll_node_t io_wait_node;  // khi chờ I/O
} task_t;

Mỗi node độc lập: queue có thể dùng ready_node mà không ảnh hưởng sleep_node.

Ưu điểm: Tách biệt dữ liệu từ cấu trúc → kernel có thể xóa task từ bất kỳ queue nào mà không ảnh hưởng các queue khác.

(4) Bản chất & Invariant – Pointer arithmetic & container_of

Khi dùng intrusive pattern, phải luôn giữ vững những nguyên lý sau:

Invariant 1: Circular doubly-linked consistency

  • Empty: head == NULL
  • Single: node->next == node && node->prev == node
  • Multiple: head->prev = tail, tail->next = head

Nếu vi phạm → duyệt circular sẽ loop vô tận hoặc trỏ vào bộ nhớ sai.

Invariant 2: Container-of calculation đúng

#define container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))

Nếu offsetof sai → pointer sai → access đến bộ nhớ không liên quan.

Ví dụ: Nếu task_t có:

struct {
    int priority;        // 4 bytes
    void (*entry)();     // 8 bytes
    dll_node_t node;     // 16 bytes (prev + next)
};

Offset của node là 12 bytes (4+8). Nếu code sai thành 4 bytes → sẽ trỏ vào entry pointer, thảm họa.

Invariant 3: Node phải luôn ở đúng memory state

  • Khi node nằm trong queue: prev/next hợp lệ
  • Khi node được remove: prev/next phải được reset (ví dụ về standalone: node->next = node; node->prev = node;)

Nếu quên reset, code còn lại có thể dùng node này lại → vi phạm Invariant 1.

(5) Hiện thực – Tại sao phải circular

Circular doubly-linked list cho phép O(1) remove mà không cần special case:

void dll_remove(dll_list_t* list, dll_node_t* node) {
    // Không cần kiểm tra "có phải head không"
    // Không cần kiểm tra "có phải tail không"
    
    // Chỉ đơn giản: rewire 4 pointers
    node->prev->next = node->next;
    node->next->prev = node->prev;
    
    // Nếu node được remove là head, update head
    if (list->head == node) {
        list->head = node->next;
        if (list->count == 1) {  // nếu chỉ có 1 node
            list->head = NULL;   // list trở rỗng
        }
    }
    
    list->count--;
    
    // Reset node về standalone (cho lần sử dụng tiếp theo)
    node->next = node->prev = node;
}

Tại sao circular tốt hơn linear?

Linear (SLL cũ):

remove(task1):
  task0->next = task1->next;
  free(task1);
  
Nhưng nếu task1 là tail? → phải check & update tail riêng
Nếu task1 là head? → phải check & update head riêng
→ 3 special cases

Circular:

remove(node):
  node->prev->next = node->next;  // ← Work luôn, dù node ở đâu
  node->next->prev = node->prev;  // ← Work luôn, dù node ở đâu
→ Code một lần, apply cho mọi vị trí

Thêm phần:

void dll_push_back(dll_list_t* list, dll_node_t* node) {
    if (list->head == NULL) {
        // List rỗng
        node->next = node->prev = node;
        list->head = node;
    } else {
        // Thêm vào sau tail (tức trước head)
        node->next = list->head;
        node->prev = list->head->prev;
        list->head->prev->next = node;
        list->head->prev = node;
    }
    list->count++;
}

Nhìn vào, mỗi dòng code đều là kết quả của circular invariant, không có special case.

(6) Liên hệ kernel – ISR xóa task thực tế

Trong kernel thực tế:

// kernel.c
typedef struct {
    int priority;
    void (*entry)(void*);
    dll_node_t ready_node;   // ← node nhúng vào task
    dll_node_t sleep_node;
    dll_node_t io_wait_node;
} task_t;

static dll_list_t ready_queue = {0};
static dll_list_t sleep_queue = {0};

// ISR: Task B hoàn thành I/O, cần xóa task A từ running queue
void isr_io_complete(task_t* task_b) {
    // Xóa task B khỏi I/O wait queue (có node pointer, O(1))
    dll_remove(&io_wait_queue, &task_b->io_wait_node);
    
    // Add task B vào ready queue
    dll_push_back(&ready_queue, &task_b->ready_node);
    
    // Preempt task A nếu task B ưu tiên cao hơn
    task_t* task_a = current_task;
    if (task_b->priority > task_a->priority) {
        // Xóa task A khỏi running, add vào ready (O(1) vì có node)
        dll_remove(&ready_queue, &task_a->ready_node);
        dll_push_back(&ready_queue, &task_a->ready_node);
        
        // Schedule task B chạy
        schedule();
    }
}

// Scheduler
void schedule() {
    if (ready_queue.head == NULL) return;
    
    dll_node_t* node = ready_queue.head;
    task_t* t = container_of(node, task_t, ready_node);
    
    dll_remove(&ready_queue, node);
    current_task = t;
    t->entry(NULL);
}

Ưu điểm ở đây:

  • ISR xóa task mà không cần search → deterministic latency
  • “Điều mà ISR cần là: có task pointer, xóa nó trong O(1). DLL Intrusive cho phép chính xác điều đó.”
  • Code không cần biết queue dài bao nhiêu

(7) Giới hạn Phase 1 – Và hướng phát triển

Vấn đề 1: Container-of phụ thuộc memory layout

Nếu task_t có:

typedef struct {
    int id;
    dll_node_t node;
} task_v1;

Offset = 4 bytes. Nhưng nếu sau này ai đó thêm trường:

typedef struct {
    int id;
    int priority;        // ← thêm trường mới
    dll_node_t node;
} task_v2;

Offset = 8 bytes. Code cũ sẽ tính toán sai.

Cách khắc phục: Compiler hỗ trợ không? Hay cần static assertion kiểm tra offset?

Vấn đề 2: Multiple nodes – quản lý dễ lẫn lộn

Một task có 3 nodes (ready, sleep, io_wait). Code bên ngoài phải chính xác biết dùng node nào:

// ✓ Đúng
dll_remove(&ready_queue, &task->ready_node);

// ✗ Sai (nhưng compiler không bắt lỗi)
dll_remove(&ready_queue, &task->sleep_node);

Đây là runtime type safety issue – C không bảo vệ chúng ta.

Hướng phát triển (Phase 2):

  • Sentinel node để loại bỏ special case rỗng
  • Type-safe wrapper macros
  • Circular variant tối ưu cache locality

(8) Insight – Tư duy kiến trúc thay đổi

Phase 1 DLL Intrusive dạy chúng ta một bài học quan trọng về tách biệt đáp ứng từ tổ chức dữ liệu. “Intrusive không làm kernel phức tạp hơn — nó chỉ làm trách nhiệm trở nên rõ ràng hơn.”

Bài học 1: Intrusive = Dữ liệu sở hữu cấu trúc, không ngược lại

Non-intrusive (SLL cũ): Kernel tạo node, quản lý node, giữ reference đến node.

Kernel: [list] owns [node] owns data

Intrusive: Dữ liệu tạo node, kernel chỉ quản lý liên kết.

Data (task): [task] embeds [node]
Kernel: [list] links [node]

Mindset khác biệt: Dữ liệu phải tự chuẩn bị để tham gia vào queue, không phải kernel bao bọc nó.

Bài học 2: Pointer arithmetic là kỹ năng cốt lõi của kernel engineer

offsetof() và container_of() không phải “mánh khóe”. Chúng là fundamental tool để tách biệt dữ liệu từ siêu dữ liệu (metadata).

Kernel thực tế (Linux, Windows, QNX) đều dùng mẫu này. Khác biệt duy nhất là Linux dùng list.h generic, Windows dùng CONTAINING_RECORD, nhưng cốt lõi là giống nhau.

Bài học 3: Circular giải quyết sự phức tạp không nhất thiết

Linear queue có các special case: head, tail, rỗng, một phần tử.

Circular loại bỏ chúng bằng cách làm mọi vị trí “giống nhau” từ góc độ pointer rewiring.

Tư duy: “Thay vì xử lý special case, thiết kế để chúng không tồn tại.”

Bài học 4: ISR latency là constraint kiến trúc thực tế

Phase 1 tồn tại vì ISR có yêu cầu: O(1) deterministic. Đó không phải “tối ưu học thuật”, mà requirement kiến trúc concrete.

Kernel engineer không chọn cấu trúc vì nó “thú vị”, mà vì nó phục vụ constraint thực tế của hệ thống.

Kết luận

Doubly Linked List Phase 1 là bước tiến từ “danh sách đơn giản” sang “kiến trúc nhận thức ISR latency”.

Nó giới thiệu intrusive pattern – một cách tổ chức dữ liệu cho phép kernel xóa task từ bất kỳ queue nào trong O(1) deterministic, không phụ thuộc độ dài queue.

Qua Phase 1, chúng ta học không chỉ “cách cài đặt DLL”, mà cách suy nghĩ về tách biệt dữ liệu từ cấu trúc kiểm soát.

Điều đó là kiến thức cơ bản để hiểu kernel thực tế – nơi mà performance không phải là tùy chọn, mà là requirement cốt lõi của hệ thống.
