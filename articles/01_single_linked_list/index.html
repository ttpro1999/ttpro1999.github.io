Single Linked List – Khi mảng không còn đủ (RTOS perspective)

📅 Published: January 7, 2026
RTOS Data Structure Kernel Linked List C

(1) Bối cảnh thực tế – Cơn đau bắt đầu

Tôi đang xây một bộ lập lịch RTOS cho hệ thống nhúng. Cần quản lý danh sách các tác vụ (task) có thể được tạo ra hoặc kết thúc bất kỳ lúc nào - sô lượng không cố định trước.

Ban đầu, cách tiếp cận tự nhiên nhất: dùng mảng tĩnh để lưu tasks. Nó hoạt động tốt cho một vài tác vụ. Nhưng rồi, trong một hệ thống thực, lỗi xảy ra:

Scenario cụ thể: Một tác vụ I/O đang chờ đọc file. Khi ISR (interrupt handler) hoàn thành I/O, nó cần xóa tác vụ khỏi danh sách “chờ I/O” trong vòng 500ns. Với mảng, xóa một phần tử ở giữa có nghĩa dồn các phần tử phía sau lên - thao tác O(n). Nếu danh sách có 100 tasks, đó là 100 lệnh assignment trong interrupt handler. Interrupt sẽ bị block quá lâu.

Điểm yếu cơ bản của mảng:

  • Xóa giữa mảng = phải dồn, O(n)
  • Mở rộng = cấp phát + sao chép, O(n)
  • Cấp phát trước = lãng phí hoặc không đủ

(2) Giải pháp ngây thơ – và tại sao nó thất bại

Mảng tĩnh:
[task0][task1][task2][task3]

Xóa task1:
[task0][task2][task3]???
           ↑↑↑ phải dồn

Mặc dù task2, task3 vẫn còn, ta buộc phải copy chúng. O(n) operation trong ISR.

Rõ ràng, mảng thiếu linh hoạt cho hệ thống động. Tôi cần một cấu trúc cho phép thêm/xóa mà không kéo theo tất cả các phần tử khác.

“Trong kernel, O(n) không phải là chậm — nó là không xác định được.”

(3) Ý tưởng cốt lõi – Liên kết mềm dẻo

Thay vì đặt tất cả tasks liên tục trong bộ nhớ, tôi có thể để mỗi task tự biết hàng xóm của nó.

Mảng (tight coupling):
[task0][task1][task2]

SLL (loose coupling):
task0 → task1 → task2 → NULL

Mỗi task sẽ giữ một con trỏ next trỏ đến task tiếp theo. Khi cần xóa task giữa danh sách, chỉ cần chỉnh sửa con trỏ từ task trước nó:

task0 → task1 → task2 → NULL

Xóa task1:
task0 → task2 → NULL
(chỉ cần: task0->next = task1->next)

Thao tác này là O(1) – chỉ thay đổi 1 con trỏ, không phụ thuộc độ dài danh sách. Hoàn hảo cho ISR.

(4) Bản chất & Invariant – Thứ không được phép sai

Để SLL vận hành đúng, những điểm sau PHẢI luôn đúng, không ngoại lệ:

Invariant 1: Head hợp lệ

  • head trỏ đến task đầu tiên, hoặc NULL nếu danh sách rỗng.
  • Nếu head sai → toàn bộ danh sách “mất dấu”.

Invariant 2: Tail chính xác

  • tail trỏ đến task cuối cùng (hoặc NULL nếu rỗng).
  • Nếu xóa task cuối mà quên cập nhật tail → tail trỏ vào task đã được free, use-after-free bug.

Invariant 3: Số lượng chính xác

  • Nếu duy trì biến count, nó phải bằng số task thực tế trong danh sách.
  • Nếu count sai → logic scheduler bị lệch (ví dụ sai số tasks sẵn sàng chạy).

Invariant 4: Con trỏ không “treo”

  • Mọi next phải trỏ đến task hợp lệ tiếp theo hoặc NULL.
  • Không được trỏ vào bộ nhớ đã bị free.

(5) Hiện thực – Tại sao phải như vậy

Tôi định nghĩa hai cấu trúc:

typedef struct sll_node {
    struct sll_node* next;
    task_t* task;           // trỏ đến task thực tế
} sll_node_t;

typedef struct {
    sll_node_t* head;
    sll_node_t* tail;
    int count;
} sll_t;

Tại sao cần tail?

// Không có tail:
void sll_push_back(sll_t* list, task_t* t) {
    sll_node_t* node = malloc(...);
    node->task = t;
    node->next = NULL;
    
    if (list->head == NULL) {
        list->head = node;
    } else {
        sll_node_t* curr = list->head;
        while (curr->next) curr = curr->next;  // ← O(n) duyệt
        curr->next = node;
    }
}

Mỗi lần thêm cuối phải duyệt từ đầu → O(n). Với kernel thêm/xóa task liên tục, đây là độ chậm không chấp nhận được.

Có tail:

void sll_push_back(sll_t* list, task_t* t) {
    sll_node_t* node = malloc(...);
    node->task = t;
    node->next = NULL;
    
    if (list->tail == NULL) {           // rỗng
        list->head = list->tail = node;
    } else {
        list->tail->next = node;        // ← O(1) nối cuối
        list->tail = node;              // cập nhật tail
    }
    list->count++;
}

O(1) thay vì O(n) – đó là lý do có tail. Đánh đổi: phải cập nhật tail kỳ cùng, nhưng với kernel, đó là giá trị vôi cứng.

Xóa task - xử lý invariant cẩn thận:

int sll_remove(sll_t* list, task_t* t) {
    sll_node_t *prev = NULL, *curr = list->head;
    
    while (curr && curr->task != t) {
        prev = curr;
        curr = curr->next;
    }
    
    if (!curr) return -1;  // không tìm thấy
    
    // Ba trường hợp đặc biệt:
    if (prev == NULL) {                    // xóa đầu
        list->head = curr->next;
        if (list->head == NULL)            // danh sách trở rỗng
            list->tail = NULL;
    } else if (curr == list->tail) {       // xóa cuối
        prev->next = NULL;
        list->tail = prev;                 // tail lùi lại
    } else {                               // xóa giữa
        prev->next = curr->next;
    }
    
    free(curr);
    list->count--;
    return 0;
}

Nhìn vào code, ba nhánh if không phải “boilerplate dư thừa” – mỗi cái đảm bảo một invariant:

  • Nhánh 1: head luôn hợp lệ
  • Nhánh 2: tail luôn chính xác
  • Tất cả: count được cập nhật

(6) Liên hệ kernel – Scheduler thực tế dùng nó như thế nào

Trong kernel.c của RTOS, ready queue được quản lý bằng SLL:

// kernel.c
static sll_t ready_queue = {0};

// ISR - Task I/O hoàn thành
void isr_io_complete(task_t* t) {
    // Xóa task khỏi I/O wait queue
    sll_remove(&io_wait_queue, t);  // O(1) thêm vào ready queue
    sll_push_back(&ready_queue, t);
    // Xong trong ~100ns, không block ISR
}

// Scheduler - chọn task chạy tiếp
task_t* sched_pick_next() {
    if (ready_queue.head == NULL)
        return NULL;                     // không có task sẵn sàng
    
    sll_node_t* node = ready_queue.head;
    task_t* t = node->task;
    
    sll_remove(&ready_queue, t);         // lấy khỏi queue
    return t;
}

Ưu điểm SLL ở đây:

  • ISR có thể xóa task từ wait queue trong O(1) → không block interrupt
  • Scheduler luôn biết có bao nhiêu tasks sẵn sàng (dùng ready_queue.count)
  • Thêm/xóa task lên xuống mà không lo sợ dồn mảng
  • “Điều quan trọng không chỉ là nhanh, mà là luôn nhanh như nhau, kể cả khi hệ thống có 10 hay 100 task.”

(7) Giới hạn – Khi nào SLL không đủ?

Vấn đề 1: Tìm kiếm chậm O(n)

Khi kernel phát triển, tác vụ cần được sắp xếp theo ưu tiên. ISR hoàn thành task, cần insert nó vào vị trí đúng theo priority:

// Với SLL, tìm vị trí đúng mất O(n):
void sll_insert_sorted(sll_t* list, task_t* t) {
    sll_node_t* curr = list->head;
    
    while (curr && curr->task->priority > t->priority)
        curr = curr->next;  // ← O(n) duyệt trong worst case
    
    // chèn vào vị trí curr
}

Nếu có 100 tasks, điều này trong ISR là không chấp nhận.

Hướng phát triển tự nhiên:

  • Không dùng simple queue, mà dùng priority queue (heap hoặc balanced tree)
  • Insert/remove sẵn có vị trí trong O(log n)
  • Cost: cấu trúc phức tạp hơn, nhưng scheduler thực tế đều làm thế này (FreeRTOS, Linux)

Vấn đề 2: Duyệt ngược

Nếu cần xóa task cuối cùng nhanh, SLL buộc phải duyệt từ đầu để tìm nút trước nó → O(n).

Hướng phát triển: Doubly Linked List (DLL)

Khác biệt cơ bản:

SLL (một chiều):
task0 → task1 → task2 → NULL
  ↑
  Muốn xóa task1: phải duyệt từ task0 (O(n) trong worst case)

DLL (hai chiều):
NULL ← task0 ↔ task1 ↔ task2 → NULL
        ↑           ↑
        prev        next
        
Muốn xóa task1: task1->prev->next = task1->next; (O(1) ngay lập tức)

Cấu trúc:

typedef struct dll_node {
    struct dll_node *next, *prev;  // có cả hai chiều
    task_t* task;
} dll_node_t;

DLL cho phép xóa node đã biết con trỏ trong O(1), nhưng tốn thêm 8 bytes mỗi node. Tuy nhiên, ở quy mô hệ thống lớn, cost này hoàn toàn đáng giá vì xóa task trong ISR sẽ luôn O(1).

(8) Insight – Những bài học từ hành trình

Thiết kế SLL không phải chỉ là “triển khai một cấu trúc”. Nó là một quyết định kiến trúc căn cứ trên use-case thực tế.

Bài học 1: Data structure là kết quả của constraint

  • Constraint: “Xóa task trong ISR phải O(1)”
  • Kết quả: SLL thay vì mảng
  • Constraint khác: “Sắp xếp priority” → kết quả khác (priority queue)

Kỹ sư kernel không chọn data structure vì “nó tuyệt vời”, mà vì nó giải quyết vấn đề cụ thể.

“Kernel engineering không phải là nghệ thuật tạo ra cấu trúc phức tạp, mà là nghệ thuật từ chối những thứ chưa cần thiết.”

Bài học 2: Invariant = rào cản giữa “đúng” và “crash”

Mảy lỗi trong kernel (race condition, use-after-free, memory leak) là kết quả của vi phạm invariant. Thói quen suy nghĩ dựa trên invariant chính là kỹ năng để viết code không “đột ngột crash”:

  • Trước khi code: “Những điều gì PHẢI luôn đúng?”
  • Khi code: “Dòng này có giữ vững invariant không?”
  • Sau khi code: “Có trường hợp nào vi phạm invariant?”

Bài học 3: “Cắt gọn” cấu trúc là điều tươi

SLL không phải là “tối ưu nhất” – nó thậm chí có điểm yếu (tìm kiếm O(n), duyệt một chiều). Nhưng đó là sự lựa chọn có ý thức: bỏ qua các tính năng không cần để giữ code đơn giản, dễ debug, dễ mở rộng sau.

Khi kernel phát triển (thêm priority scheduling), ta nâng cấp lên priority queue, chứ không thêm 10 công cụ khác vào SLL.

Bài học 4: “Đánh đổi” là cách sống của kernel engineer

Tail pointer = +8 bytes mỗi list, nhưng push_back từ O(n) → O(1). Đó là deal tốt.

Doubly-linked = +8 bytes mỗi node, nhưng xóa từ “cần tìm prev” → O(1). Đó cũng là deal.

Kernel engineer không tìm “giải pháp hoàn hảo”, mà tìm “đánh đổi hợp lý cho bối cảnh này”.

Kết luận

Single Linked List sinh ra từ một cơn đau thực tế: ISR cần xóa task trong O(1), mảng không làm được. SLL là lựa chọn tự nhiên khi bạn hiểu rõ:

  • Vấn đề cụ thể là gì
  • Invariant cần bảo vệ
  • Những đánh đổi bạn sẵn sàng chấp nhận

Nhưng SLL cũng không phải “bước đến cuối”. Khi hệ thống phát triển, ta sẽ cần priority queue, doubly-linked list, hoặc cả hai. Điều quan trọng là hiểu tại sao, không phải chỉ biết cái gì.

Đó là cách suy nghĩ của một kernel engineer.
